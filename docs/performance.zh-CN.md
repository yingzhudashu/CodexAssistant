# 性能与稳定性

## 目标与资源预算

服务端隔离基准 ingest p95≤50ms，任务查询 p95≤100ms；30分钟预热后RSS末次较起始增长≤50MiB。Android可控网络前台恢复目标≤5秒、进程唯一连接。桌面100线程空闲轮询p95≤300ms、活跃p95≤2s仍是目标，尚无100/1000真实线程全负载验收，不能写成已达标。

|位置|边界|
|---|---|
|桌面轮询|2秒间隔、不重入；8线程并发，每线程4详情RPC，理论32 RPC，单请求15秒|
|生命周期读取|每线程每轮2MiB，残行1MiB，之后增量读取|
|outbox|5000事件；变化批量持久化后发送；每轮最多100条/约1秒预算，单HTTP10秒；退避上限60秒|
|服务入口|HTTP/WS入站128KiB；认证订阅15秒；实时缓冲256KiB；回放500条后完整快照|
|控制/交互|控制请求256条/30秒，待答及终态各1000；初始交互逐帧等待写完|
|Trace|OTel队列2048、批256；桌面日志队列256、双文件各约5MiB；Android队列和父索引各100|
|Android UI|有序任务单项移动；回执累积1000、详情单页缓存20；Compose LazyColumn|

## 已实施优化

SQLite复用固定prepared statements，同一快照仅序列化一次。诊断不重复同步写入，OTel批量用一事务；失败不改变已提交业务结果。桌面outbox批量持久化、上传有预算，Trace上传不占用轮询等待。线程详情缓存与生命周期投影分离，保留准确的过期判断。

桌面未变化任务不重建DOM，只更新状态/时间区域；Intl.DateTimeFormat复用，Markdown交给成熟解析器。Android回执积累防止StateFlow合并丢失结果，任务更新二分定位，避免每次全列表排序；设置复用HTTP客户端，通知仅在显示内容变化时刷新。

Android通知变化保留最多1000任务的最新revision，系统发送按300ms间隔串行，最新内容替换同任务待发内容，提交后释放记录；活动任务通知保留最近40项，任务数据不清除。通知处理使用有10秒超时的短时CPU锁，空闲释放；WebSocket库心跳15秒，用更快的失效检测换取额外网络唤醒。未授予电池豁免或系统强杀时不保证息屏实时性，通知延迟与手机耗电需要分别评估。

## 本机实测口径

Node v24.15.0 / Windows x64。`npm run perf:server`在独立临时SQLite使用Fastify inject，包含同进程请求生成和响应对象；不是公网请求，也不是独立服务稳态RSS。脚本通过 `--expose-gc` 在测量前和快照批次之间主动回收，避免压测客户端长期持有完整快照造成假性 RSS 增长；仍同时输出 GC 前峰值 `rssBeforeGcBytes` 和 GC 后 `rssBytes`，两者都用于诊断。

|---|---:|---:|---:|
|1000事件更新同一任务|总960.70ms，p50 0.84ms，p95 1.31ms，查询0.62ms|总942.37ms，p50 0.81ms，p95 1.25ms，查询0.72ms|总984.05ms，p50 0.84ms，p95 1.33ms，查询0.60ms|

最近的历史样本所有门槛均通过；更早样本曾因CPU 81.73%、事件循环 p95 83.36ms 超限失败，说明同机负载/运行抖动会影响短时测量，不能把通过样本解释成稳定服务SLA。报告来自 Node v24.15.0 / Windows x64，主机为 Windows 10.0.26300、12th Gen Intel(R) Core(TM) i7-12650H、16逻辑CPU、总内存约15.74GiB。可再生原始报告按仓库清理规则删除，历史汇总保留于此。

本次全面审查开始时以未修改源码重新运行基准：并发 ingest p95 17.23ms、任务查询 p95 3.34ms、单核 CPU 63.94%、事件循环 p95 43.12ms、GC 后 RSS 增长 67.78MiB，均通过脚本门槛。审查期间模拟器及全量 Gradle 构建同时争用本机资源时，曾测得 ingest p95 37.85ms、CPU 81.58%、事件循环 p95 53.67ms而失败；停止无 ADB 设备的模拟器后，再测得 ingest p95 26.60ms、任务查询 p95 3.64ms、CPU 69.81%、事件循环 p95 43.65ms、RSS 增长60.80MiB并通过。它说明共享主机的并发负载显著影响短时 CPU/事件循环指标，不能把失败简单归因于 ingest 实现或将一次通过解释成SLA。

完成所有构建和模拟器尝试后再次串行复测：同任务 ingest p95 1.36ms、20并发不同任务 ingest p95 17.22ms、任务查询 p95 3.41ms、单核 CPU 67.74%、事件循环 p95 48.23ms、GC 后 RSS 增长59.93MiB，所有脚本门槛通过。事件循环余量约1.77ms，短测仍对主机负载敏感，不能外推为稳定延迟保证。

较早和中间样本保留作波动对照，不与最新值混算。基准脚本对单/并发 ingest p95≤50ms、任务查询 p95≤100ms、GC后 RSS 增长≤128MiB、单核 CPU≤80%、事件循环 p95≤50ms 直接断言失败。RSS 峰值单独输出，不能把 GC 后数字解释为瞬时峰值；该脚本仍不代表生产 unit 的公网 SLA。

Electron实际renderer千条合成任务约百毫秒渲染；无变化更新验证输入节点、卡片节点和焦点不变，430×600无页面横向溢出。具体本轮数字见原始报告，单次渲染不是所有机器的性能保证。

## 持续同步

当前源码的30分钟隔离HTTP/WS耐久验收已通过：持续1800.043秒，1000任务、4512事件、5次计划重连、7次快照；最终游标与事件数一致，最终任务数为1000。跳过首分钟预热后RSS范围97.72–114.09MiB，稳定区间起点至末次从109.13MiB降至99.22MiB（变化-9.91MiB），末次累计单核CPU0.68%，最慢一分钟ingest p95为23.36ms。测试使用临时SQLite及合成任务，不访问历史用户数据库、真实Codex或手机。逐分钟原始报告为可再生产物，验收数字已保留在版本控制文档中并按清理规则删除。

测试使用临时SQLite、随机本地HTTP端口和合成任务，不访问历史用户数据库、真实Codex或手机，也不覆盖生产反代、磁盘和unit资源限制。RSS采用进程工作集采样，可能受GC及操作系统调整影响，不作为所有环境的永久内存承诺。

## 复现与观测

`npm run perf:server`断言p95门槛及快照游标/数量；`npm run test:endurance`运行30分钟并输出 `artifacts/acceptance/server-endurance.json`，供审查期间留存和计算，完成后可由 `npm run clean` 删除。health提供RSS、累计CPU、订阅数、数据库计数、Trace导出/直传失败及保留清理数；CPU占用应从相邻累计采样计算。

业务事件/任务不自动删，数据库磁盘随时间增长；Trace保留不会自动VACUUM。生产长期容量、慢磁盘、真实大线程与OEM后台属于后续环境验收范围，详见[验收记录](acceptance.zh-CN.md)。
